# Дифференцируемый граф: как структура учится градиентом

Документ описывает третий этап проекта: переход от **рукописного** графа
(умножение в столбик, собранное вручную) к графу, **топологию которого находит
обучение**.

Рукописный граф умножения отвечает на вопрос «а работает ли вообще разреженный
целочисленный граф». Дифференцируемый граф отвечает на следующий: **может ли
структура вычисления быть найдена, а не придумана человеком.**

---

## 1. Что именно обучается

Граф — это список узлов. У каждого узла две вещи, которые нужно выбрать:

1. **операция** из фиксированного набора;
2. **два входа** — ссылки на выходы предыдущих узлов (или на входы задачи).

Всё остальное — жёсткая механика: узлы исполняются в топологическом порядке,
рёбра смотрят строго назад, никаких циклов.

Набор операций:

| Операция | Формула на `{0,1}` | Смысл |
|---|---|---|
| `AND`  | `a·b` | конъюнкция |
| `OR`   | `a + b − a·b` | дизъюнкция |
| `XOR`  | `a + b − 2ab` | исключающее или |
| `NAND` | `1 − a·b` | отрицание конъюнкции |
| `ADD`  | `a + b` | арифметическое сложение |
| `MUL`  | `a·b` | арифметическое умножение |
| `COPY` | `a` | тождество |

Полиномиальные формы выбраны не случайно: на `{0,1}` они **точно** совпадают с
булевыми операциями, но при этом дифференцируемы. Именно это позволяет
пользоваться градиентом, не выходя из булева домена.

---

## 2. Мягкий выбор: Gumbel-Softmax

Выбор «какая операция» — это дискретное решение, у него нет производной.
Стандартный приём — заменить его на **мягкий** выбор с температурой:

```
w = softmax(logits / τ)
значение_узла = Σ_k w_k · op_k(a, b)
```

При большом `τ` распределение почти равномерное (исследование), при малом —
почти одно-hot (использование). Температура отжигается по косинусу от `2.0` до
`0.1`.

Но мягкий граф на выходе даёт не то, что нам нужно: нужен **жёсткий** граф из
конкретных операций. Поэтому используется **Gumbel-Softmax со
straight-through estimator** (`hard=True`):

* вперёд считается настоящий one-hot (жёсткий выбор);
* назад градиент течёт так, как будто выбор был мягким.

Это и есть «в начале мягкий выбор, по мере обучения — жёсткий»: к концу
обучения температура мала, и softmax сам становится почти одно-hot, а
straight-through гарантирует, что исполняется ровно та структура, которая
обучена.

То же самое — для выбора входов каждого узла (два независимых softmax'а по
множеству «все предыдущие узлы + входы задачи») и для выбора выходов.

### Реализация

`src/python/diffgraph/model.py`:

```python
class DifferentiableGraph(nn.Module):
    op_logits  # [N, K]        — какая операция в узле j
    src_logits # [N, 2, S]     — какие два входа у узла j
    out_logits # [O, S]        — какой узел подаётся на выход o
```

Маска `src_mask` запрещает узлу смотреть вперёд: `-1e9` в логитах для всех
источников с индексом `>= n_inputs + j`. Так DAG соблюдается **по построению**,
а не проверкой после обучения.

## 3. Три проблемы, которые пришлось решить

### 3.1 «Холодные» узлы

При жёстком выходе узел, не подключённый ни к одному выходу, получает **ровно
нулевой градиент**. Он не может ни измениться, ни подключиться — мёртв.

Лечение: держать **выход мягким**, а узлы жёсткими. Тогда у каждого узла есть
ненулевой вес в выходе, а значит и градиент, через который он может «пробиться».

Флаг: `--soft-out` (включён по умолчанию).

### 3.2 Детерминированный градиент

Задача крошечная — 16 строк таблицы истинности. На полном батче градиент
детерминирован, и оптимизация залипает в первом же локальном минимуме.

Лечение: **мини-батч** из 8 примеров (`--batch 8`). Появляется шум, который
выбивает из мелких ям.

### 3.3 Согласованные изменения

Градиент двигает логиты каждого узла **независимо**. Он хорошо находит
структуру «в целом», но не умеет делать несколько согласованных изменений
сразу.

Это видно на сложении. Лучшее, что находит чистый градиент, — **93.75% (15 из
16)**:

```
s0 = a0 ^ b0
s1 = a1 ^ b1 ^ c1        c1 = a0 & b0
s2 = a1 & b1             ← не хватает слагаемого c1 & (a1 ^ b1)
```

Осталось добавить один узел `AND(c1, a1^b1)` и подмешать его в `s2`. Но пока
узел не подключён к выходу, его градиент равен нулю, а подключение — отдельное
дискретное действие. Градиент такой пары шагов не видит.

### 3.4 Добивка структуры

Лечение — стандартное для DARTS-подобных методов: после дифференцируемого
поиска архитектуру **дискретизируют и доучивают**. Здесь «доучивание» —
локальный поиск по правкам структуры (`src/python/diffgraph/refine.py`).

Ключевая деталь, которая делает его дешёвым: на 4 входах таблица истинности
состоит из 16 строк, значит значение любого узла — это **16-битная маска**, а
операция над узлами — одна побитовая операция над целым числом:

```python
if op == "AND": v = va & vb
elif op == "OR": v = va | vb
elif op == "XOR": v = va ^ vb
elif op == "NAND": v = ~(va & vb) & full
```

Проверка целой структуры — несколько десятков таких операций. Поэтому можно
честно перебрать **всё** соседство и брать строго лучшее:

* смена операции узла;
* переподключение одного входа узла;
* смена выхода;
* добавление узла;
* **вставка** узла прямо в выход: `out[o] = op1(out[o], op2(a, b))`.

Последняя правка составная и нужна потому, что одиночное «добавить узел» ничего
не меняет в точности — узел ещё ни к чему не подключён. Если улучшений нет,
делается случайный **нейтральный** шаг, чтобы пройти через плато.

На практике добивка занимает **один шаг** и доли секунды.

## 4. Задачи

| Задача | Входы | Выходы | Что делает |
|---|---|---|---|
| `parity4` | `a0 a1 a2 a3` | 1 | чётность 4 бит (XOR всех входов) |
| `add2` | `a0 a1 b0 b1` | `s0 s1 s2` | сумма двух 2-битных чисел (`0..6`) |

Обе задачи — полный перебор таблицы истинности: 16 входов, проверка «все
выходы верны».

## 5. Результаты

### parity4 — решена чистым градиентом

```
n4 = XOR(in0, in3)
n5 = XOR(in1, in2)
n6 = XOR(n5, n4)
out0 = n6
```

**3 вычислительных узла, 6 связей, 100% (16/16), бит-в-бит.**
Найдено на первом же рестарте за **1.22 с** — добивка не понадобилась.

Полученное дерево — сбалансированное: `(a0^a3) ^ (a1^a2)`. Никто не задавал
форму дерева, градиент сам выбрал парное объединение.

### add2 — градиент + добивка

Лучший результат чистого градиента: **93.75% (15/16)**. После одного шага
добивки — **100% (16/16), 48/48 бит**.

```
n4  = AND(in0, in2)      c1 = a0 & b0
n5  = OR(n4, in3)        c1 | b1
n6  = AND(n5, in1)       a1 & (c1 | b1)
n7  = XOR(in1, in3)      a1 ^ b1
n8  = XOR(in0, in2)      s0
n9  = XOR(n7, n4)        s1 = a1 ^ b1 ^ c1
n10 = AND(in3, n4)       b1 & c1
n11 = OR(n6, n10)        s2
```

**8 вычислительных узлов, 16 связей.** Это полный сумматор, но записанный не в
учебной форме `a1b1 | a1c1 | b1c1`, а в виде `a1(c1|b1) | b1c1` — то же самое
по таблице истинности, но на один узел короче. Такую факторизацию никто не
закладывал.

### Сводка по рестартам (add2, 8 рестартов)

| Рестарт | 1 | 2 | 3 | 4 | 5 | 6 | 7 | 8 |
|---|---|---|---|---|---|---|---|---|
| Точность | 93.75% | 75% | 75% | 87.5% | 87.5% | 75% | 87.5% | 75% |

Видно характерное распределение: 75% — это «сложение без переноса из младшего
разряда», сильный аттрактор; 87.5% и 93.75% — всё более близкие к истине
варианты. Именно поэтому нужны и рестарты, и добивка.

## 6. Проверка в C++

Python обучает, но **не судит**. Итоговый вердикт выносит C++-движок, и таблицу
истинности он считает **сам**, независимо от Python:

```cpp
if (name == "parity4") {
    t.expected.push_back({ in[0] ^ in[1] ^ in[2] ^ in[3] });
} else {
    const int32_t a = in[0] + 2 * in[1];
    const int32_t b = in[2] + 2 * in[3];
    const int32_t s = a + b;
    t.expected.push_back({ s & 1, (s >> 1) & 1, (s >> 2) & 1 });
}
```

Если бы эталон брался из Python-файла, проверка не проверяла бы ничего.

```bash
cd src/cpp
.\run.ps1 -Graphs          # исполнить все results/graphs/*.json
```

Вывод:

```
    задача      узлов связей  точность вердикт
    add2           12     16   100.00%      OK
    parity4         7      6   100.00%      OK
```

Дополнительно C++ проверяет, что **все значения графа остались в `{0,1}`**:
если бы обучение ушло в арифметику и выдало, например, `2`, побитовые операции
движка перестали бы совпадать с полиномиальными операциями обучения, и граф
молча разошёлся бы. Проверка домена это ловит.

### Бит-в-бит на стороне Python

Ещё до экспорта Python сверяет два исполнения одной структуры:

* **float** — как считает обученная модель;
* **int** — как посчитает C++ (`apply_int`, точное зеркало `switch` из движка).

Если они расходятся хотя бы на одном входе, кандидат отбрасывается
(`bit_exact = нет`). Так в C++ уходит только то, что уже проверено.

## 7. Формат экспорта

`results/graphs/<task>.json`, версия 1:

```json
{
  "format": "diffgraph",
  "version": 1,
  "task": "parity4",
  "n_inputs": 4,
  "n_outputs": 1,
  "nodes": [
    {"op": "INPUT"},
    {"op": "INPUT"},
    {"op": "INPUT"},
    {"op": "INPUT"},
    {"op": "XOR", "in": [0, 3]},
    {"op": "XOR", "in": [1, 2]},
    {"op": "XOR", "in": [5, 4]}
  ],
  "outputs": [6],
  "meta": {}
}
```

Индексация **сквозная**: `0..n_inputs-1` — входы, дальше вычислительные узлы.
Это сделано специально, чтобы индексы Python-графа совпадали с `Node::in[]`
C++-движка один в один и никакого пересчёта при загрузке не требовалось.

Перед экспортом граф **обрезается**: узлы, недостижимые от выходов,
удаляются. Индексы входов при этом не меняются.

## 8. Запуск

```bash
cd src/python
..\..\.venv\Scripts\python.exe -m diffgraph --all      # обучить обе задачи
..\..\.venv\Scripts\python.exe -m diffgraph --task add2 --restarts 16
..\..\.venv\Scripts\python.exe -m diffgraph --help
```

Ключевые флаги:

| Флаг | По умолчанию | Что делает |
|---|---|---|
| `--nodes N` | 8 | вычислительных узлов в графе |
| `--steps N` | 3000 | шагов обучения на рестарт |
| `--restarts N` | 8 | число независимых рестартов |
| `--lr` | 0.15 | скорость обучения |
| `--tau-start` / `--tau-end` | 2.0 / 0.1 | отжиг температуры |
| `--hard-start` | 0.3 | доля шагов до включения straight-through |
| `--batch N` | 8 | мини-батч (0 = полный) |
| `--soft-out` / `--no-soft-out` | вкл | мягкий выход (лечит «холодные» узлы) |
| `--refine N` | 120 | шагов дискретной добивки (0 = выключить) |
| `--json` | выкл | записать сводку в `results/diff_graph_training.json` |

Код завершения `0` - только если **все** задачи решены на 100% и прошли проверку
бит-в-бит.

## 10. Что это доказывает и чего не доказывает

**Доказывает:**

* топологию вычислительного графа можно найти градиентом, без перебора;
* Gumbel-Softmax + straight-through даёт жёсткий граф, пригодный к исполнению;
* найденная структура совпадает с известными схемами (XOR-дерево, полный
  сумматор) и иногда оказывается короче учебной;
* граф, обученный в Python, исполняется целочисленным C++-ядром с точностью
  100% и без нейросетей.

**Не доказывает:**

* что метод масштабируется на задачи, где нет полного перебора таблицы
  истинности (16 строк — это очень мало);
* что градиент справляется сам: на `add2` понадобилась дискретная добивка;
* ничего про «интеллект» - это по-прежнему алгоритмическая задача.

Следующий честный шаг - задача, где таблицу истинности нельзя перебрать
целиком (например, 8-битное сложение с переносом), и проверка, масштабируются
ли и градиент, и добивка.
