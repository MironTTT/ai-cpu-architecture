# Устройство графового ядра

Документ описывает `src/cpp/graph_evolve.cpp`: модель данных, инварианты
исполнения, алгоритм каскадного сумматора и разбор ошибки Python-версии.

---

## 1. Модель данных

### Узел

```cpp
struct Node {
    Op      op;        // тип операции
    uint8_t arity;     // сколько входов реально используется (0..2)
    int32_t in[2];     // индексы входных узлов (для Const: in[0] = значение)
};
```

12 байт, `trivially copyable`. Это не случайность, а требование к эволюции:
копия графа, скрещивание и мутация — это операции над плоским массивом, без
указателей, без аллокаций на узел и без обхода по ссылкам.

### Операции

| Op | Семантика | Входов |
|---|---|---|
| `Input` | значение подаётся извне | 0 |
| `Add` | `in[0] + in[1]` | 2 |
| `Mul` | `in[0] * in[1]` | 2 |
| `Mod10` | `in[0] % 10` — младшая десятичная цифра | 1 |
| `Div10` | `in[0] / 10` — перенос в следующую колонку | 1 |
| `Copy` | `in[0]` | 1 |
| `Const` | константа из `in[0]` | 0 |

Никаких `float`, никаких матричных умножений, никаких библиотек.

### Граф

```cpp
class Graph {
    std::vector<Node>    nodes;    // в порядке исполнения
    std::vector<int32_t> inputs;   // индексы узлов Op::Input
    std::vector<int32_t> outputs;  // индексы узлов-ответов
};
```

## 2. Инвариант исполнения

**Все рёбра указывают строго назад:** `in[k] < i` для узла с индексом `i`.

Это топологический порядок, и он даёт главное преимущество:

* исполнение — один линейный проход по массиву, без рекурсии и без очереди;
* не нужно проверять «а посчитан ли уже вход»;
* нет ни одной ветки, зависящей от данных, кроме `switch` по типу операции
  (предсказуемый переход по таблице).

Инвариант поддерживается:

* `repair()` — восстанавливает его после мутаций и скрещивания; битые рёбра
  подключаются к `Const 0`, а не отбрасываются, поэтому структура графа
  переживает изменения;
* `mutate()` — перенаправляет рёбра только на более ранние узлы;
* `crossover()` — сохраняет индексы хвоста, конфликты лечит `repair()`.

### Исполнение

```cpp
for (size_t i = 0; i < n; ++i) {
    switch (nodes[i].op) {
        case Op::Add:  values[i] = values[in0] + values[in1]; break;
        case Op::Mul:  values[i] = values[in0] * values[in1]; break;
        case Op::Mod10: values[i] = values[in0] % 10; break;
        ...
    }
}
```

* `memset(values, 0, ...)` в начале — одна операция на весь буфер;
* буфер `values` переиспользуется между примерами: **ни одной аллокации
  внутри цикла бенчмарка**;
* `% 10` и `/ 10` компилируются в умножение на магическую константу и сдвиг,
  без инструкции `idiv`;
* `Add` выполняется через `uint32_t`, `Mul` — через `int64_t`, чтобы
  переполнение в эволюционировавших графах не было UB.

Сложность: **O(N)** на пример, где N — число узлов (55 для 4 цифр).

## 3. Каскадный сумматор (ripple-carry)

### Схема

```
p[i][j]   = a_i * b_j                  — d² частичных произведений
colsum[k] = Σ p[i][j] по i + j == k    — колонка умножения в столбик

s_k     = colsum[k] + carry_{k-1}
digit_k = s_k % 10
carry_k = s_k / 10
```

Перенос `carry_k` — **целое число, а не цифра**. Для 4×4 сумма в колонке
достигает 351, значит перенос доходит до 35. Именно поэтому «перенос в одну
цифру» — неверная модель: перенос надо хранить как полноценное значение и
подавать его на вход суммы следующей колонки.

В графе это буквально два узла на колонку:

```
        colsum[k] ──┬──> MOD10 ──> digit_k
                    │
        carry_{k-1} ┴──> ADD ──> s_k ──> DIV10 ──> carry_k ──┐
                                                              │
                                                   (в колонку k+1)
```

Внутри колонки частичные произведения складываются **сбалансированным
деревом**, а не цепочкой: меньше глубина зависимости — больше параллелизма
на уровне инструкций.

### Разбор на примере `1234 × 5678`

Цифры младшими вперёд: `a = [4,3,2,1]`, `b = [8,7,6,5]`.

| k | частичные произведения колонки | `colsum` | `carry_{k-1}` | `s_k` | `digit_k` | `carry_k` |
|---|---|---|---|---|---|---|
| 0 | 4·8 = 32 | 32 | 0 | 32 | **2** | 3 |
| 1 | 4·7 + 3·8 = 28+24 | 52 | 3 | 55 | **5** | 5 |
| 2 | 4·6 + 3·7 + 2·8 = 24+21+16 | 61 | 5 | 66 | **6** | 6 |
| 3 | 4·5 + 3·6 + 2·7 + 1·8 = 20+18+14+8 | 60 | 6 | 66 | **6** | 6 |
| 4 | 3·5 + 2·6 + 1·7 = 15+12+7 | 34 | 6 | 40 | **0** | 4 |
| 5 | 2·5 + 1·6 = 10+6 | 16 | 4 | 20 | **0** | 2 |
| 6 | 1·5 = 5 | 5 | 2 | 7 | **7** | 0 |
| 7 | — | 0 | 0 | 0 | **0** | 0 |

Цифры младшими вперёд: `2 5 6 6 0 0 7 0` → **7006652**. Проверка: `1234 × 5678 = 7006652`. ✅

### Что делала Python-версия

Тот же пример без переносов (то есть с `carry ≡ 0`):

| k | 0 | 1 | 2 | 3 | 4 | 5 | 6 | 7 |
|---|---|---|---|---|---|---|---|---|
| `s_k` | 32 | 52 | 61 | 60 | 34 | 16 | 5 | 0 |
| `digit_k` | 2 | 2 | 1 | 0 | 4 | 6 | 5 | 0 |

Получается `5640122` вместо `7006652` — ровно то, что выдавал старый код.

**Причина:** в `build_mul_graph()` два прохода. Первый собирает `colsum[k]`,
второй создаёт узлы `MOD10`/`DIV10` и заполняет `carries[k+1]`. Но `carries[k]`
читается в **первом** проходе, когда он ещё `None` для всех `k`. Перенос
считается и сохраняется — и никогда не используется. Каскад разорван.

Отсюда и неверная формулировка исходной задачи: ошибка проявляется не при
сумме > 99, а уже при сумме ≥ 10, то есть практически всегда. Проверка на
2000 случайных примеров: **2000 из 2000 неверных**.

## 4. Сколько стоит граф

Для `d = 4`:

| Компонент | Узлов |
|---|---|
| входы `a_i`, `b_j` | 8 |
| частичные произведения `MUL` | 16 |
| сложения в колонках (деревья) | 9 |
| добавление переноса | 7 |
| `MOD10` (цифры) | 8 |
| `DIV10` (переносы) | 8 |
| **итого** | **55** |

Связей: `16·2 + 15·2 + 16·1 = 78`. «Параметров» (узлы + связи) — **133**.

Память: `55 · 12 = 660` байт на узлы + `55 · 4 = 220` байт на значения
≈ **880 байт** на весь граф вместе с рабочим буфером. Это в ~40 раз меньше
одного 32-КБ L1-кэша.

Для сравнения: 3B-модель в Q4 — это ~2 ГБ весов, которые надо прочитать из RAM
на каждый токен.

## 6. Эволюция

Операторы не знают ничего о задаче: граф для них — просто данные.

```cpp
mutate(graph, rate, rng);              // смена операции / перенаправление ребра
crossover(parentA, parentB, rng);      // префикс A + хвост B
evolve(seed, train, pop, gens, rate);  // турнирный отбор + элитизм
```

Что показывает демо (`--evolve --from-random`, 32 особи, 15 поколений):

```
fitness до эволюции: 0.0963
gen   0  best=0.1425
gen  10  best=0.1638
gen  14  best=0.1663
```

То есть механика работает и fitness растёт, но с нуля алгоритм умножения за
десятки поколений не открывается. Это честный результат и понятная граница
текущего этапа: **структуру умножения мы задали руками, эволюция пока только
оптимизирует и портит**. Следующий шаг — обучение структуры с нуля.

## 7. Ограничения

* `Mod10`/`Div10` — десятичные примитивы «под задачу». Для логики и кода
  понадобится другой базис (сравнение, выбор, битовые операции).
* Граф строится вручную, а не находится поиском.
* Один поток, без SIMD. Векторизация «по примерам» (а не по узлам) даст ещё
  кратный рост — граф одинаков для всех примеров, значит его можно исполнять
  над 8/16 примерами одновременно.
* Сравнение с 3B-моделью по «примеров/сек» условно: задачи разные.
