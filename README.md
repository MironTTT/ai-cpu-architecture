# Графовое ядро (CPU-Native AI)

Гипотеза проекта: **интеллект — это структура вычислений, а не количество параметров.**
Вместо плотных матриц, где каждый вес перемножается с каждым, мы строим разреженный
граф элементарных целочисленных операций. Такой граф целиком живёт в кэше CPU,
не требует GPU и не «читает» гигабайты весов из RAM на каждом шаге.

Проект идёт по трём этапам, и все три пройдены:

1. **Рукописный граф.** Умножение двух 4-значных чисел на графе из **55 узлов /
   78 связей** — точность **100%**, скорость **~11.7 млн примеров/сек** на обычном
   ноутбуке.
2. **Стандартизация.** Единая структура каталогов, независимые реализации на C++
   и Python, документация, воспроизводимые замеры.
3. **Дифференцируемый граф.** Топология больше не пишется руками: её находит
   **градиент** (Gumbel-Softmax + straight-through), после чего жёсткий граф
   экспортируется в C++ и проверяется там **независимо**. Чётность 4 бит и
   сложение двух 2-битных чисел — **100%** без нейросетей в исполнении.

### Обучение структуры (дифференцируемый граф)

```bash
cd src/python
..\..\.venv\Scripts\python.exe -m diffgraph --all

# затем — исполнение обученных графов в C++-ядре:
cd ..\cpp
.\run.ps1 -Graphs
```

```
    задача      узлов связей  точность вердикт
    add2           12     16   100.00%      OK
    parity4         7      6   100.00%      OK
```

Как это работает: каждый узел выбирает операцию (`AND, OR, XOR, NAND, ADD, MUL,
COPY`) и два входа; выбор делается мягким (Gumbel-Softmax) и постепенно
«затвердевает» по мере отжига температуры. Найденная структура сохраняется в
`results/graphs/*.json` и исполняется тем же целочисленным движком, что и
умножение. Подробности — в [docs/differentiable_graph.md](docs/differentiable_graph.md).

### Python-часть (baseline-эксперименты с LLM)

```bash
cd src/python
```

## Проверить самому

Всё, что ниже, проверяется с нуля одной командой. Нужны только MSVC (или `g++` в
`PATH`) и `.venv` с `torch` — больше ничего.

```powershell
cd src\cpp
.\run.ps1 -Train
```

Что произойдёт: `run.ps1` найдёт интерпретатор из `.venv`, обучит оба графа
(~100 с на одном потоке CPU), затем соберёт C++-ядро (если его нет) и исполнит
обученные графы в нём. Код возврата `0` — только если **обе** задачи решены на
100% и прошли сверку с целочисленной семантикой.

Отдельные шаги, если хочется покрутить параметры:

```powershell
cd src\cpp

.\run.ps1                       # умножение 4x4, 1000 примеров + замер
.\run.ps1 --digits 9            # умножение 9x9
.\run.ps1 --json                # + results/graph_cpp_results.json

.\run.ps1 -Train --task parity4 --restarts 1 --steps 1500   # быстро, ~3 с
.\run.ps1 -Train --task add2 --restarts 16                  # длиннее, ~3 мин
.\run.ps1 -Train --no-soft-out                              # без мягкого выхода
.\run.ps1 -Train --refine 0                                 # без добивки

.\run.ps1 -Graphs               # только исполнить уже обученные графы
.\run.ps1 -Rebuild -Graphs      # пересобрать ядро и исполнить
```

Про `--refine 0`: это самый показательный запуск. Чистый градиент доводит `add2`
до **87.5–93.75%** и останавливается — код возврата будет `1`. Это не поломка, а
ровно тот разрыв, который закрывает дискретная добивка. `parity4` решается
градиентом полностью, ей добивка не нужна.

Нерешённый граф сохраняется как `<задача>.unsolved.json` и **не затирает**
рабочий `<задача>.json` — чтобы эксперимент не портил уже проверенный результат.

### На что смотреть

1. **Структура графа** — это и есть «найденный алгоритм». У `parity4` должно
   получиться XOR-дерево из 3 узлов, у `add2` — схема сумматора из 8 узлов.
2. **`Таблица истинности`** в выводе C++ — эталон считается **внутри C++**, а не
   берётся из Python. Если бы эталон приходил из файла, проверка была бы пустой.
3. **`значения в {0,1}: да`** — все промежуточные значения остались булевыми.
   Иначе побитовые операции C++ разошлись бы с обучением.
4. **`Совпадение с целочисленной семантикой C++: да`** — Python до экспорта
   сверяет float-исполнение с целочисленным.

### Как убедиться, что проверка не «пустая»

Испортите граф руками — правильный ответ обязан стать `FAIL`, а код возврата
`1`:

```powershell
cd src\cpp

# меняем XOR на AND во всём графе parity4
(Get-Content ..\..\results\graphs\parity4.json -Raw).Replace('"XOR"', '"AND"') |
    Out-File $env:TEMP\broken.json -Encoding utf8

.\graph_evolve.exe --load $env:TEMP\broken.json
echo $LASTEXITCODE      # ожидается 1
```

Так же ловятся ссылка узла на самого себя (`граф не является корректным DAG`) и
опечатка в имени задачи (`неизвестная задача: ...`).

## Что именно было исправлено

В Python-версии перенос **считался, но никуда не подключался**: узлы `DIV10`
создавались во втором проходе, уже после того как все суммы колонок были
собраны. В момент сборки `colsum[k]` список `carries[k]` был пуст, поэтому
сумма следующей колонки собиралась **без** переноса.

Из-за этого граф ошибался не только при сумме в колонке > 99, а практически
всегда (ошибка появляется уже при сумме ≥ 10). Проверка на 2000 случайных
примеров: **2000 из 2000 неверных**.

В C++-версии каскад замкнут явно:

```
s_k     = Σ p[i][j] (i+j=k)  +  carry_{k-1}
digit_k = s_k % 10
carry_k = s_k / 10
```

`carry_k` — это **целое число, а не цифра**: для 4×4 максимум суммы в колонке
достигает 351, значит перенос доходит до 35. Поэтому перенос хранится как
обычный узел `DIV10` и подаётся на вход суммы следующей колонки — каскад
корректен при любом размере суммы (100, 324, 1000).

Подробный разбор с арифметикой на примере `1234 × 5678` — в
[docs/graph_core.md](docs/graph_core.md).

### Логические задачи (граф найден обучением)

| Задача | Узлов | Связей | Точность | Как получена | Примеров/сек |
|---|---|---|---|---|---|
| `parity4` (чётность 4 бит) | 7 | 6 | 100% (16/16) | чистый градиент, 1 рестарт, 1.2 с | ~83.5 млн |
| `add2` (сумма двух 2-битных) | 12 | 16 | 100% (16/16) | градиент 93.75% + 1 шаг добивки | ~45.6 млн |

Обе структуры найдены без подсказок о форме решения: `parity4` — сбалансированное
XOR-дерево `(a0^a3)^(a1^a2)`, `add2` — полный сумматор, записанный короче
учебной формы: `s2 = a1(c1|b1) | b1c1`.

> Скорости у логических задач несопоставимы с умножением напрямую: графы
> крошечные, и число измеряет в основном стоимость цикла по 16 строкам таблицы
> истинности.

Замеры: Intel Core i5-11400H, MSVC 19.43, `/O2`, один поток, без SIMD-интринсиков.
Подробности и методика — в [docs/benchmarks.md](docs/benchmarks.md) и
[docs/differentiable_graph.md](docs/differentiable_graph.md).

> Сравнение «11.7 млн/сек против 0.07 задач/сек у 3B-модели» — **условное**: это
> разные задачи (арифметика против GSM8K). Оно показывает разницу в стоимости
> одного шага вычисления, а не превосходство в общем интеллекте.

## Готовность к эволюции

Структура данных спроектирована так, чтобы граф был «геномом», а не рукописным
кодом:

* `Node` — 12 байт, trivially copyable: копирование/скрещивание — это `memcpy`;
* инвариант «все рёбра смотрят строго назад» даёт линейное исполнение без проверок;
* `mutate()` — смена операции или перенаправление ребра;
* `crossover()` — префикс узлов одного родителя + хвост другого;
* `repair()` — лечит граф после любых структурных изменений, не отбрасывая его;
* `evolve()` — турнирный отбор + элитизм.

Проверить: `./graph_evolve --evolve --from-random --gens 50`.
